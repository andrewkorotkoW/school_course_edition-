# EduQuest

Образовательная платформа для школьников. Полная концепция возрастных зон — в [docs/CONCEPT.md](docs/CONCEPT.md) (описывает более ранний взгляд на продукт, часть решений там уже пересмотрена — см. ниже).

## Текущее направление (пересмотрено 20.10.2026)

Проект разворачивается от детского игрового MVP (квесты + магазин + 3D-городок) к платформе
с админкой:

- **Админка** собирает программу обучения из областей/предметов, которые выбирает администратор.
- Для основных предметов есть **готовые шаблоны** — не начинать с нуля каждый раз.
- Охват — школьная программа **1–5 класс**.
- Ученик проходит собранную программу — существующий механизм "квест → задания → проверка"
  переиспользуется как единица содержания программы.
- Эндпоинты админки и ученика: `/admin/programs` (GET — список, POST — создать программу из
  выбранных квестов), `/admin/programs/{id}` (GET), `/admin/programs/{id}/assign` (POST —
  назначить программу ученику по его id), `/students/{student_id}/quests` (GET — какие квесты
  видит ученик с учётом назначенной ему программы).

Игровой слой (баллы, магазин построек, 3D-сцена) из прошлой версии MVP удалён осознанно
(20.10.2026) — см. «История решений» ниже. Модель данных (Subject/Quest/Task/Progress) оставлена
и переиспользуется.

## Стек

Backend — Python/FastAPI + SQLAlchemy + PostgreSQL. Frontend — Next.js (React, TypeScript).
Dev-окружение — Docker Compose. Стек выбран как продолжение уже обкатанного в этом репозитории,
без смены ради новой фичи.

## Структура репозитория

```
backend/            FastAPI-приложение
  app/
    core/            конфигурация
    db/               подключение к БД, сид тестовых данных
    models/          SQLAlchemy-модели (Parent, Student, Subject, Quest, Task, Progress, Program)
    schemas/         Pydantic-схемы
    api/routes/      эндпоинты, включая admin.py (программы) и students.py (квесты ученика)
  tests/             backend-тесты (pytest) — первые тесты в проекте
frontend/            Next.js-приложение
  app/                страницы (/, /quest/[id]) и admin/ — админка сборки программы
docs/
  CONCEPT.md           концепция возрастных зон и игровых механик (частично устарела, см. выше)
docker-compose.yml
.env.example
```

## Быстрый старт

```bash
cp .env.example .env
docker compose up --build
```

- Backend: http://localhost:8000 (`/health`, `/subjects`, `/subjects/{slug}/quests`,
  `/quests/{id}/tasks`, `/tasks/{id}/check`, `/students/quests/complete`, `/students/{student_id}/quests`,
  `/admin/programs`, `/admin/programs/{id}`, `/admin/programs/{id}/assign`)
- Frontend: http://localhost:3000 (`/admin` — админка сборки программы)

Засеять контент — предметы, демо-ученика, по квесту на каждый класс (1–5) с заданиями по
математике и русскому:

```bash
docker compose exec backend python -m app.db.seed
```

Сид также создаёт демо-программу «Математика и русский, 1 класс» (только из квестов 1 класса) и
сразу назначает её демо-ученику — без этого шага `/students/1/quests` вернул бы пустой список.

> На хосте установлен Node v12 — для фронтенда он слишком старый (Next.js требует 18+). Поэтому
> frontend собирается и запускается только внутри Docker (образ `node:20-alpine`) — локально
> `npm install`/`npm run dev` без контейнера работать не будет, пока вы не обновите Node на машине.

## Что ещё не реализовано

- Админка есть, но без своей авторизации — `/admin` на фронтенде и эндпоинты `/admin/programs*`
  открыты без входа, разграничения ролей нет.
- Назначение программы — это `student.program_id`, то есть **1 ученик = 1 программа одновременно**:
  нет истории назначений и нельзя вести несколько программ параллельно (повторное назначение
  просто перезаписывает текущую).
- Ученик без назначенной программы не видит ничего: `GET /students/{id}/quests` намеренно
  возвращает пустой список, а не все квесты и не ошибку.
- Нет миграций (Alembic) — таблицы создаются напрямую при старте backend.
- Нет авторизации/реальных ученических аккаунтов — везде используется захардкоженный
  `student_id=1` (сид создаёт для него демо-ученика).
- Контента пока по одному квесту (3 задания) на класс и предмет, 1–5 класс и по-прежнему только
  два предмета (математика и русский) — достаточно, чтобы проверить механику заданий и сборку
  программы, мало для реального использования.
- Нет родительского/учительского интерфейса.

## История решений

**Версия 1 (питомец).** Единственный питомец, растущий через 5 стадий с Phaser-анимацией
(процедурные фигуры). Отказались — геометрические фигуры не дают приемлемого визуального
качества, а Phaser-анимация добавляла хрупкости (игра сама ставится на паузу при потере вкладкой
фокуса).

**Версия 2 (городок с магазином).** Баллы за квесты → покупка построек (сначала эмодзи, потом
настоящие низкополигональные 3D-модели из набора Kenney, CC0) → городок на 3D-сцене
(Three.js/react-three-fiber). Решало проблему визуала версии 1 и подтверждалось живым разбором
рынка (docs/CONCEPT.md писался позже с опорой на этот анализ) — у немецкого Anton и ClassDojo
Dojo Islands похожая механика работает на десятках миллионов пользователей.

**Версия 3 (текущая, с 20.10.2026).** Сменился фокус: вместо детского игрового продукта —
платформа с админкой, которая собирает программу обучения из шаблонов по предметам, 1–5 класс.
Игровой слой версии 2 удалён целиком (код сохранён в истории git, в коммитах до 20.10.2026, если
понадобится вернуться). Модель контента (Quest/Task) оставлена — то, что раньше было "квестом с
наградой", теперь просто единица программы.

**Версия 4 (реализация, 20.10.2026).** Решение версии 3 реализовано: появилась модель `Program`
(заголовок + диапазон класса + набор квестов), эндпоинты `/admin/programs*` и страница `/admin`,
через которую администратор отмечает нужные квесты по предмету и классу и назначает получившуюся
программу ученику. Модель Quest/Task не менялась — Program это новый слой группировки поверх неё,
который выбирает администратор, а не ещё одна параллельная модель контента.

**Версия 4.1 (персистентность, 20.10.2026).** Добавлена модель `TaskProgress` (отдельно от
квестовой `Progress`) — фиксирует, какие задания ученик уже решил верно. `GET /quests/{id}/tasks`
принимает `student_id` и возвращает по каждому заданию `completed`; страница квеста на фронтенде
резюмирует с первого нерешённого задания вместо перезапуска с начала при обновлении страницы.
Попутно найден и исправлен баг: при повторном заходе на уже полностью пройденный квест страница
зависала на "Загрузка..." навсегда — проверка `tasks/index` в рендере стояла раньше проверки
`finished`, а `index` для уже завершённого квеста никогда не выставлялся.
